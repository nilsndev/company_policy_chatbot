**Issues hit and fixed while wiring this up (worth knowing if you touch this area):**
- `DATABASE_URL` needed the Supabase **Session pooler** host (`aws-0-<region>.pooler.supabase.com:5432`, username `postgres.<project-ref>`), not the direct `db.<ref>.supabase.co` host — that host is IPv6-only and unreachable on this network (same class of issue as the Neo4j TLS note below). Updated in `.env.example`.
- A password with `#`/`&`/`$` breaks a Postgres URI even when the `.env` line parses fine — `#` starts a URI *fragment* and everything after it (host, port, dbname) silently gets dropped by the URI parser. Percent-encode special characters in the password segment (`$`→`%24`, `#`→`%23`, `&`→`%26`), or use libpq keyword=value format instead of a URI.
- On Windows, `uvicorn app.main:app` creates its event loop *before* importing `app.main`, so a policy fix inside that module (e.g. switching off the default `ProactorEventLoop` for psycopg's async driver) is too late. Added `run.py` as the local dev entrypoint — it sets `asyncio.WindowsSelectorEventLoopPolicy()` before calling `uvicorn.run()`, which works. Use `python run.py`, not the bare `uvicorn` CLI, for local dev on Windows.
- This Supabase project has "Confirm email" on by default, which blocks a fresh signup from getting a session immediately (and free-tier email sending rate-limits fast under repeated test signups). Disabled it for this dev project (Authentication → Providers → Email) so signup → chat works in one step, matching the PRD's v1 scope (no auth-hardening requirement).
- A local-state sync bug in `ChatShell.tsx`: starting a new thread didn't reset `loadedConversationId`, so returning to a previously-loaded conversation afterward skipped the reload guard and showed a blank pane. Fixed by resetting it alongside `conversationId` in `startNewThread`.

Persistence lives in `app/services/db.py` alongside the existing chat/profile helpers, not inline SQL in the orchestrator — keeps `ingestion.py` unit-testable by monkeypatching `db.*` the same way `test_chat.py` already does.
- [x] Job status `queued|processing|ready|failed` surfaced to caller — `GET /api/v1/policies` (`app/api/policies.py`) returns each policy's latest job status. `app/workers/ingest.py` + root `worker.py` is the second native process that polls `ingestion_jobs` and drives `queued → processing → ready|failed`.
- [x] Chat answers grounded in vector retrieval, with citations — `app/services/retrieval.py` does a plain pgvector `<=> ` top-k query (**no user/department filter** — that's the Neo4j RBAC graph, M4, not implemented yet). `app/api/chat.py` packs retrieved chunks into a numbered context block, requires the model to cite `[n]`, and emits `event: citation` SSE frames (parsed from the model's own `[n]` references) before `event: done`; citations persist on the `messages.citations` jsonb column (`supabase/migrations/0004_messages_citations.sql`) so they survive a history reload. Frontend (`ChatShell.tsx`) renders a small "Sources" list under grounded replies.

**Explicitly not done here (do not read as "isolation is done"):** every authenticated employee currently sees every policy's chunks regardless of department — RLS on `policies`/`policy_chunks`/`ingestion_jobs` only checks `auth.uid() is not null`. Department/role scoping via the Neo4j RBAC graph is M3/M4.

**Issues hit and fixed while wiring this up:**
- Corpus loading is a seed script (`scripts/seed_corpus.py`), not an HTTP upload endpoint — there's no admin-role concept yet, and PRD's non-goals already frame v1 seeding as script-driven, not a UI. Deliberate scope call, not an oversight.
- `pgvector`'s psycopg3 adapter (`pgvector.psycopg.register_vector_async`) must be called per-connection, not once globally — since `AsyncConnectionPool` hands out pooled connections, every function that binds a Python list to a `vector` column/parameter (`db.replace_policy_chunks`, `retrieval.retrieve_chunks`) registers it on its own `pool.connection()` block.
- `register_vector_async` alone isn't enough: it only registers a dumper for `pgvector.Vector`/`numpy.ndarray`, not plain Python `list` — a raw `list[float]` query param falls through to psycopg's default array dumper (`double precision[]`), which fails on `vector <=> double precision[]` (`UndefinedFunction`, no matching operator). `INSERT` didn't fail because pgvector defines an implicit assignment cast from array to `vector` for column targets, but the `<=>` *operator* has no such cast — so the retrieval query surfaced this and the insert path didn't. Fix: wrap every embedding param in `pgvector.Vector(...)` explicitly, both on write (`db.replace_policy_chunks`) and read (`retrieval.retrieve_chunks`). Caught by live-testing the retrieval query directly against the real DB, not by the mocked unit tests — worth a live spot-check on any future vector-param code.
- The worker checks `policies.content_hash` against the *stored* chunk's `content_hash` before downloading/parsing the file at all — reruns of `seed_corpus.py` over an unchanged corpus stay cheap (queue drains without re-embedding anything).

- [x] Seed script populates the graph from the same policy corpus/metadata used in M2 — `scripts/seed_graph.py` reads the same 24 corpus files (`chunking.parse_document`), resolves each slug to its Postgres `policies.id` (so `Policy.id` matches across both stores, per `graph` skill), and writes `APPLIES_TO`/`SUPERSEDES`/`REFERENCES` edges. Run after `seed_corpus.py`; re-running is safe (each write is a `MERGE`/reset-then-`MERGE`, matching `upsert_profile`'s idempotency).
- [x] Cypher queries for: department/role scoping, supersedes resolution, references lookup — `neo4j.allowed_policy_ids` (department match or company-wide or `compliance_officer` role, per PRD §6.1/§6.3), `neo4j.resolve_current_version` (walks a `SUPERSEDES` chain to the head), `neo4j.related_policy_ids` (capped `REFERENCES` lookup). None of these are wired into `retrieval.py`/`chat.py` yet — that's M4; M3 only makes the graph queryable.

**Notes:**
- `references` is a new frontmatter field (`app/services/chunking.py` `DocumentMeta.references`, a list of slugs, defaulting to `[]`) — the corpus only had `supersedes` before this milestone. Added hand-authored `references:` lists to 12 of the 24 corpus files based on real prose cross-references already in the text (PRD §9: hand-authored, not auto-extracted). `references` is graph-only — it doesn't touch the Postgres `policies` table or the M2 ingestion/chunking path, which still discards `DocumentMeta` entirely past `chunk_markdown`.
- `Department`/`Role` nodes are never seeded standalone — they're created on demand via `MERGE` from `upsert_employee`/`upsert_policy`, same pattern as `policies` upserting on `slug` in `seed_corpus.py`.

## M4 — Hybrid retrieval + RBAC (loop 2 complete, loop 4)
- [x] Retrieval pipeline updated to the 5-step flow in PRD §6.3 (vector candidates → graph filter/enrich → LLM) — `app/services/retrieval.py` now: (1) pgvector search with the employee's department/role in the *same* SQL query as the similarity `ORDER BY` (`_vector_search`), (2) `neo4j.allowed_policy_ids` as an independent second filter on the survivors, (3) `_resolve_superseded` swaps a stale policy's chunk for its current version (dropping it if no visible current version exists), (4) `_enrich_with_references` adds up to `RELATED_LIMIT=2` supplementary chunks from `REFERENCES`-linked policies, each still re-checked against both layers since a related/current-version policy can belong to a different department than the original match. `app/api/chat.py` passes `user.id` + `request.app.state.neo4j_driver` through; the system prompt now tells the model scoping/supersedes are already handled and marks supplementary excerpts as "(Related policy)".
- [x] Fixed a fail-closed bug in `neo4j.allowed_policy_ids` while wiring this up: it used `MATCH (e:Employee {id: ...})` instead of `OPTIONAL MATCH`, so any employee without a graph node yet (profile saved but the best-effort sync in `profile.py` hasn't landed) got zero rows back — denying even company-wide policies, not just department-scoped ones.
- [x] RLS policies in Supabase updated (`supabase/migrations/0005_policy_rbac_rls.sql`) to mirror the same department/role scoping. **Important caveat, worth knowing for the interview walkthrough:** the backend connects via the Supabase session-pooler `postgres.<project-ref>` role, which — like any Postgres table owner — bypasses RLS (`supabase` skill: "Service role bypasses RLS: always add user_id filters in server queries too"). So this migration does not restrict the backend's *own* queries; the real, always-enforced isolation for this app's actual query path is the two independent layers above (SQL WHERE-clause + Neo4j traversal). The RLS migration is still correct/worth having as defense-in-depth against any future direct-table access (a supabase-js call from the frontend, an admin UI), and is literally what PRD §6.5 asks for — just don't describe it as "the thing stopping the FastAPI backend" without this nuance.
- [x] Isolation test suite: `tests/test_retrieval_rbac.py` — verifies the SQL filter is parameterized from the server-resolved profile (never client input), that an unassigned profile (Sam persona) only ever matches company-wide policies, that the graph layer independently blocks cross-department content even if a candidate hypothetically survived the SQL filter (the literal PRD §6.5 IT-vs-Clinical scenario), that a `compliance_officer` sees every department, and covers supersedes-swap + references-enrichment. 6 new tests, all passing (27 total across the suite).
- [x] Superseded-policy and cross-reference questions spot-checked live against the real seeded corpus/Neo4j/Ollama stack (migrated, seeded corpus + graph, ran API + worker, signed up throwaway IT/Clinical/compliance_officer employees). This caught and fixed two real bugs the unit tests (built against fakes) couldn't have caught:
  - `_resolve_superseded` deduped to **one chunk per policy**, which silently dropped a second relevant section of a still-current policy whenever that policy was also the supersedes target — a live "remote work from another country" query returned only Remote Work Policy v2's *domestic*-approval section because the *international* section (same v2 policy, different chunk) got deduped away as a "duplicate". Fixed: only stale (superseded) chunks get dropped/substituted now; multiple genuine chunks of a current policy are all kept.
  - The references-enrichment step compared candidate ids against `seen_policy_ids` computed **before** the `primary[:k]` truncation, so a policy that matched the vector search directly but lost out to the `k` cutoff was wrongly treated as "already in context" and its legitimate REFERENCES-linked chunk got silently skipped. Fixed: `seen_policy_ids` is now recomputed from the truncated `primary` list.
  - Confirmed live: an IT & Security employee's "detect a security incident?" question correctly enriches with the allowed reference (Password and Access Management Policy) while the graph independently excludes the cross-department reference (Data Breach Notification Policy, Compliance & Risk) — the exact department-mismatch-on-a-related-policy scenario the design accounts for. Confirmed live: IT/Clinical employees never see each other's department-only content (empty citations, "policy corpus doesn't cover this"); a `compliance_officer` sees Clinical content despite being in Compliance & Risk.
  - Separately observed (not a retrieval bug, noted for later): `llama3.2:3b` sometimes fails to use a correct, present context chunk (e.g. claimed no policy covers international remote work when the international-remote-work chunk was in its context) — a generation-quality limitation flagged already in PRD §9, out of scope for M4, relevant to M6 eval / prompt tuning.
  - Also noticed: `app/main.py`/API process never calls `logging.basicConfig` (unlike `worker.py`, which does) — `chat.py`'s `logger.exception(...)` on a retrieval failure may not be reliably visible in practice. Not fixed here (M4 is retrieval/RBAC correctness, not observability) — worth a follow-up if silent ungrounded-fallback failures need to be debuggable in prod.

## M5 — Multi-turn + polish (loop 3)
- [x] History/summary budget for long threads — `app/services/conversation_memory.py` (`get_context`): the raw working window is every message after `conversations.summary_through` (or all, if no summary yet), capped at a rough `RAW_WINDOW_TOKEN_BUDGET=3000`-token heuristic (`len(text)//4`, not the model's real tokenizer — good enough for budgeting). Only when that window is over budget does it fold everything except the last `KEEP_RECENT=6` turns into a rolling summary via one extra `LLMClient.stream_chat` call, persisted on `conversations.summary`/`summary_through` (`supabase/migrations/0006_conversation_summary.sql`, `db.update_conversation_summary`) — triggered on crossing the budget, not every message, per the `conversation-memory` skill. `app/api/chat.py` appends the summary (if any) to the system prompt and sends the kept raw turns + new message as history.
- [x] Stop cancels the in-flight stream cleanly — `chat.py`'s `event_stream` now holds the `llm.stream_chat(...)` async generator in a variable and calls `await stream.aclose()` in its `finally` block. Previously, breaking out of the `async for` loop on client disconnect just abandoned the generator, which left the underlying httpx request to Ollama open until Python happened to garbage-collect it — not "cleanly" cancelled. Verified live: aborted a long ("2000-word essay") generation after 3 tokens, then immediately sent a trivial follow-up straight to Ollama — it returned in 0.65s instead of queuing behind the abandoned generation, confirming Ollama's inference slot was actually freed, not just abandoned by the client.
- [x] New thread doesn't leak prior thread context — `chat.py` only calls `db.list_messages` when `body.conversation_id` is truthy; a new thread (`conversation_id: None`) gets `prior = []` unconditionally, never a filtered/truncated view of another thread. Covered by `test_chat_new_thread_does_not_include_other_conversations_history` (asserts `db.list_messages` is never even called) and confirmed live via the multi-turn check below.
- Live spot check (throwaway employee, real Supabase/Neo4j/Ollama stack): turn 1 told the assistant "my favorite color is teal"; turn 2 in the same conversation, asking "what is my favorite color?", correctly answered "teal" — confirming history/summary context actually reaches the model end to end, not just at the unit-test level.
- New unit tests: `tests/test_conversation_memory.py` (budget/no-op, `summary_through` exclusion, fold-and-persist) and two additions to `tests/test_chat.py` (continuing-conversation includes summary + history; new-thread isolation). 32 tests total, all passing.

## Notes / decisions log
- Neo4j is used for **both** GraphRAG (policy relationships) and RBAC (department/role scoping) — user decision, see [`CLAUDE.md`](CLAUDE.md) stack table.
- LLM + embeddings are local via Ollama for v1; hosted-provider swap is explicitly deferred, not assumed.
- Graph relationship extraction is hand-authored in the seed corpus, not auto-extracted — see PRD §9 for why.
- **Docker is not used for local dev** (unsupported on the current network) — Supabase and Neo4j run as hosted free-tier cloud dev instances instead (Supabase Cloud project, Neo4j Aura Free); everything else runs as native processes. See `local-dev` and `docker` skills.
